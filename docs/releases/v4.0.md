# Release v4.0

## Major architectural changes
v4.0 represents the culmination of the M04 integration effort, migrating the application from a legacy monolithic script (`ChatController.ts`) to a modular, robust Agent Runtime architecture (M03). 

This release activates the following Agent Subsystems natively in production:
- **Retriever**: Standardized vector search utilizing `VectorStore` and `KnowledgeStore` abstractions.
- **Context Builder**: Modular context assembly system guaranteeing strict LLM context budgets.
- **Execution Pipeline**: Robust tool dispatch system with automated validators, normalizers, and checkpointing.
- **Reflection**: Real-time passive observation and execution scoring framework.
- **Learning**: Evaluation engine capable of suggesting long-term knowledge promotions and memory updates based on execution outcomes.

## Architecture Evolution
**Before v4.0**
Legacy Chat Pipeline

**After v4.0**
Retriever -> ContextBuilder -> ExecutionPipeline -> Reflection -> Learning -> LLM

## Migration summary
All Agent Runtime subsystems were wrapped in Adapter classes (`RetrieverAdapter`, `ContextBuilderAdapter`, `ExecutionIntegrationService`) to cleanly integrate with the existing streaming response flow. The production integration was achieved by enabling a suite of feature flags, immediately routing traffic to the modular architecture while retaining the legacy code securely behind `else` conditionals for 100% rollback capability.

## New capabilities
- **Modular Tool Execution**: Tools are now registered via a standardized `ToolRegistry`, validating inputs natively before execution.
- **Background Reflection**: The system now silently evaluates the success and quality of every tool execution, identifying potential mistakes or improvements.
- **Learning Insight**: The system evaluates reflections to recommend items for long-term memory or permanent codebase knowledge promotion.

## Breaking changes (if any)
There are no breaking changes for end-users. All legacy workflows, prompts, and streaming responses are behaviorally equivalent, utilizing exact format mappers (e.g. `PromptContextMapper`).

## Upgrade notes
- The underlying architecture is now completely provider-agnostic and relies strictly on unified interfaces (`EmbeddingProvider`, `VectorStore`, `Tool`, etc.).

## Known limitations
- **Memory Consumption**: Reflections and Learning Decisions are currently stored in unbounded in-memory arrays.
- **Passive Learning**: The Learning subsystem does not yet automatically promote content to the long-term PostgreSQL `KnowledgeStore` or `MemoryStore`, pending a dedicated ingestion pipeline in M05.
